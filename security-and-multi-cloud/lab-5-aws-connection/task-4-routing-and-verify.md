# Task 4 - 라우팅·보안 구성과 통신 검증 🟧🟦

> ⚠️ **터널이 붙어도 라우팅과 규칙이 없으면 통신되지 않습니다.** 네 곳을 모두 손봐야 합니다.

## 4-1. 🟧 AWS 쪽 두 가지

1. VPC → [라우팅 테이블] → VPC의 라우팅 테이블 선택 → [경로 전파] 탭 → [경로 전파 편집] → VGW **활성화**.
2. [라우팅 편집]에서 `10.10.0.0/16` → 대상 `vgw-aws-userNN` 경로를 직접 추가합니다.
3. EC2 → [보안 그룹] → `ec2-aws-test-userNN`의 보안 그룹 선택 → [인바운드 규칙 편집].
4. 유형 **모든 ICMP - IPv4**, 소스 `10.10.0.0/16` 추가. 이어서 규칙을 하나 더 추가합니다 — 유형 **SSH(22)**, 소스 `10.10.0.0/16`. 두 규칙을 함께 저장합니다. (SSH는 4-3에서 EC2에 들어가 반대 방향을 확인할 때 씁니다. 이 EC2는 공인 IP가 없어 터널로만 접근됩니다.)

> ⚠️ **Lab 1~3에서 만든 Hub-Spoke 때문에 한 단계가 더 있습니다.** 스포크 VM의 UDR이 `0.0.0.0/0`을 방화벽으로 보내고 있어서, AWS로 가는 트래픽도 방화벽을 거칩니다. 방화벽이 기본 거부이므로 **명시적으로 허용하지 않으면 터널이 UP이어도 ping이 안 됩니다.** 이게 앞의 네트워크 설계와 하이브리드 연결이 만나는 지점입니다.
>
> ⚠️ **"터널은 UP인데 ping이 안 된다"면 여기부터 봅니다.** 터널은 IKE 협상만 성공하면 UP이 됩니다. **어디로 보낼지는 터널이 아니라 아래 세 가지가 정합니다.**
>
> 1. **LNG 주소 공간이 실제 VPC 대역과 같은가** — Task 3에서 넣은 `172.31.0.0/16`이 Task 1에서 만든 VPC 대역과 일치해야 합니다. IDC 연습용 값(`192.168.0.0/16`)을 잘못 넣으면 게이트웨이가 AWS로 가는 길을 모릅니다.
> 2. **피어링의 게이트웨이 전송 설정** — Lab 4 Task 1 마지막 단계에서 켜둔 두 체크박스. 안 켜져 있으면 돌아오는 패킷이 스포크를 못 찾습니다.
> 3. **위 표의 네 가지** — 경로 전파 · 보안 그룹 · 방화벽 규칙 · NSG
>
> 💡 **어디서 죽는지 바로 보는 방법** — 포털에서 `Network Watcher` → [네트워크 진단 도구] → [연결 문제 해결] → 원본 = 스포크 VM, 대상 = EC2 사설 IP, 프로토콜 = ICMP. 홉 단위로 짚어줍니다.
>
> 다만 **게이트웨이 홉에 나타나는 `RouteMissing`은 무시하셔도 됩니다.** Network Watcher가 상대 클라우드까지는 조회할 수 없어 S2S VPN 구간에서 항상 뜨는 표시입니다. **왼쪽 「연결 테스트」의 프로브 성공/실패 숫자**를 보세요 — 그게 실제 결과입니다.

## 4-3. 통신 검증

1. 🟦 Azure VM1에 SSH로 접속합니다. — **접속이 안 되면** Lab 3 Task 3의 SSH 예외 경로(`내IP/32 → 인터넷`)가 있는지 확인하세요. 앞 Lab에서는 됐는데 지금 안 된다면 **내 공인 IP가 바뀌었을 가능성**이 큽니다 — whatismyip에서 다시 확인해 경로를 갱신합니다.
2. AWS EC2로 ping을 보냅니다.
3. traceroute로 경로를 확인합니다.

- [ ] Azure VM → AWS EC2 ping 성공

> 💡 **(설명 포인트) 경로가 비대칭입니다.** AWS→Azure 인바운드는 VGW에서 피어링을 타고 VM으로 직행하지만, VM의 응답은 UDR 때문에 방화벽을 경유합니다. 앞서 본 비대칭 라우팅이 실제로 벌어지는 장면인데, 방화벽 규칙이 양방향을 허용하므로 통신이 성립합니다.
