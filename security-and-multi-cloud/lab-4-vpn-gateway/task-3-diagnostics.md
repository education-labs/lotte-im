> 상태 프로브는 **게이트웨이 인스턴스가 살아 있는가**를 묻는 것이지, 터널이 붙었는지를 묻는 게 아닙니다. 그래서 온프레미스 장비 없이도 응답합니다.
>
> 실무에서 이 구분이 중요합니다. 터널이 Down일 때 **내 게이트웨이 문제인지 상대편 문제인지**를 가르는 첫 갈래가 이 프로브입니다. 응답하면 "내 쪽은 멀쩡하다"는 근거가 생기고, 조사 범위가 상대편·경로로 좁혀집니다.

1. 브라우저 새 탭에서 첫 번째 공용 IP의 상태 프로브 URL을 엽니다.
2. 인증서 경고가 나오면 [고급] → [계속]으로 진행합니다.
3. 정상 응답이 오는지 확인합니다.
4. **두 번째 공용 IP의 8083 포트**도 같은 방식으로 확인합니다.
5. 게이트웨이 → [진단 설정] → [진단 설정 추가]에서 로그를 Log Analytics로 보냅니다.
6. 게이트웨이 → [VPN 문제 해결] 메뉴 **위치만** 확인합니다.
7. `vnet-hub-krc-prod-userNN` → [서브넷] → GatewaySubnet에 NSG·경로 테이블이 **없는지** 확인합니다.

```bash
# 첫 번째 인스턴스
https://<pip-vgw-1-userNN의 IP>:8081/healthprobe

# 두 번째 인스턴스 (활성-활성)
https://<pip-vgw-2-userNN의 IP>:8083/healthprobe
```

> ⚠️ **[VPN 문제 해결] 메뉴는 지금 단계에서 유의미한 결과를 주지 않습니다.** 실제 연결을 진단하는 도구라 상대편이 없는 지금은 실패가 정상입니다. **메뉴 위치만 확인**하고 넘어가세요 — 실제 진단은 Lab 5에서 AWS 터널이 붙은 뒤에 동작합니다.
>
> ⚠️ 응답이 아예 없으면 ① 게이트웨이가 비정상 ② GatewaySubnet에 NSG가 붙어 있음 중 하나입니다. Basic SKU는 원래 응답하지 않지만 우리는 VpnGw2AZ이므로 해당 없습니다.

- [ ] 상태 프로브(8081)가 응답하는가 — 연결이 "연결 중"이어도 응답해야 정상
- [ ] **두 번째 IP의 8083**도 응답하는가 (활성-활성 확인)
- [ ] 진단 설정을 켰는가
- [ ] GatewaySubnet에 NSG가 없는가
- [ ] GatewaySubnet에 경로 테이블이 없는가

> ➡️ **다음: Lab 5** — 방금 만든 이 게이트웨이(`vgw-hub-krc-prod-userNN`)에 **AWS를 연결**합니다. 새로 만들지 않고 [연결]을 하나 더 추가하는 방식입니다. **메모한 공용 IP 두 개를 준비해 두세요.**
