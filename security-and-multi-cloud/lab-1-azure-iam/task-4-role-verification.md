# Task 4 - 역할 차이와 상속 검증

Task 3에서 준 권한이 **실제로 어떻게 동작하는지** 직접 로그인해서 확인합니다.

## 4-1. 내 액세스 확인

1. `rg-iam-user**` → [액세스 제어(IAM)] → **[내 액세스 확인]** 탭.
2. 드롭다운에서 `dev-user**`, `view-user**` 을 각각 골라 어떤 역할이 보이는지 확인합니다.
3. **[역할 할당]** 탭에서 각 할당의 **'범위' 열**을 봅니다 — `이 리소스` 와 `상속됨(구독)` 이 구분되어 표시됩니다.

## 4-2. 읽기 권한자로 로그인해 보기

1. 브라우저 **시크릿 창**에서 `https://portal.azure.com` 접속 → `view-user**` 으로 로그인 (첫 로그인 시 암호 변경).
2. `rg-iam-user**` 이 보이는지 확인합니다.
3. 그 안에서 **[만들기]** 로 아무 리소스나 만들어 봅니다 → **권한 오류로 차단**되는 것을 확인합니다.
4. [액세스 제어(IAM)] → [추가] 버튼이 **비활성**인 것을 확인합니다.

## 4-3. 기여자로 로그인해 보기

1. 시크릿 창에서 `dev-user**` 으로 로그인.
2. `rg-iam-user**` 안에 리소스를 하나 만들어 봅니다 → **성공**합니다.
3. [액세스 제어(IAM)] → [역할 할당 추가] 를 시도합니다 → **비활성 / 거부**됩니다.

> ❗ **소유자와 기여자를 가르는 결정적 차이가 여기입니다.** 기여자는 리소스를 다 만들고 바꾸지만 **권한은 못 줍니다.** 권한 위임까지 하려면 소유자 또는 사용자 액세스 관리자가 필요합니다.

## 4-4. 상속 확인 — 상위 범위의 권한은 아래로 내려간다

> ⚠️ 이 단계는 **구독 범위에 역할을 할당할 권한**(소유자 또는 사용자 액세스 관리자)이 필요합니다. 공용 구독이라 권한이 없다면 **강사 시연으로 대체**하고, 아래 ⚠️ 설명만 확인하세요.

1. 관리자 계정으로 돌아와, **구독** 범위 [액세스 제어(IAM)] 에서 `sec-view-user**` 그룹에 **읽기 권한자**를 할당합니다.
2. 다시 `view-user**` 으로 로그인하면 **구독 아래 모든 리소스 그룹**이 보이는 것을 확인합니다.
3. 확인 후 **구독 범위의 할당은 제거**합니다 (다음 Task에 영향을 주지 않도록).

> ⚠️ **상위 범위(구독)에 준 권한은 그 아래(리소스 그룹·리소스) 전체에 자동으로 내려갑니다.** 여러 할당을 가지면 권한은 **전부 합쳐집니다.** 그래서 "일단 구독에 기여자" 같은 습관이 위험합니다 — 필요한 최소 범위에만 주세요.

## 4-5. ★ 두 권한 시스템이 별개임을 확인

1. `dev-user**` (구독/RG 기여자) 로 로그인한 상태에서 **Entra ID → [사용자] → [새 사용자]** 를 시도합니다.
2. **만들 수 없습니다.**

> ❗ **이 Lab에서 가장 중요한 확인입니다.** 리소스 권한(Azure RBAC)을 아무리 많이 줘도 **디렉터리를 건드릴 수는 없습니다.** 사용자를 만들려면 **Entra 역할(사용자 관리자)** 이 따로 필요합니다. 구독 소유자여도 마찬가지입니다.
>
> 반대도 성립합니다 — 전역 관리자여도 기본적으로는 구독 리소스가 보이지 않습니다.

- [ ] 읽기 권한자로 리소스 생성이 차단되는가
- [ ] 기여자로 리소스 생성은 되지만 **역할 할당은 안 되는가**
- [ ] 구독에 준 권한이 하위 RG로 내려오는 것을 확인했는가 (확인 후 제거)
- [ ] ★ RBAC 권한만으로는 **사용자 계정을 만들 수 없다**는 것을 확인했는가
