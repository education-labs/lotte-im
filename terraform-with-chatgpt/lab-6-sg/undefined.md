# 항목 설명

**CIDR 대신 보안그룹을 참조하는 이유**: `10.0.11.0/24에서 오는 트래픽 허용`처럼 CIDR로 규칙을 쓰면, 그 대역에 속한 모든 리소스(의도하지 않은 것 포함)가 자동으로 허용 대상이 됩니다. 반면 "App SG가 붙은 리소스에서 오는 트래픽만 허용"으로 쓰면, 실제로 App SG가 붙어 있는 리소스만 정확히 허용되고, 나중에 App 서버가 오토스케일링으로 늘거나 IP가 바뀌어도 규칙을 수정할 필요가 없습니다. Terraform에서는 `security_groups`(EC2-Classic 스타일이 아닌 `vpc_security_group_ids`/`source_security_group_id`) 방식으로 다른 보안그룹의 ID를 인바운드 규칙의 소스로 지정하면 됩니다.

**SSH를 `0.0.0.0/0`이 아니라 본인 IP로 제한하는 이유**: 22번 포트를 전 세계에 열어두면 무차별 대입 공격(brute force)의 대상이 되기 쉽습니다. 실무에서는 SSH를 사내망 대역이나 VPN, 혹은 배스천 호스트로만 제한하는 것이 기본입니다. 이 Lab에서는 간단히 본인 IP `/32`로 제한해 "출처를 좁히는" 습관을 들입니다.

**egress를 명시적으로 써야 하는 이유(Terraform의 함정)**: AWS 콘솔에서 보안그룹을 새로 만들면 기본적으로 "모든 아웃바운드 허용" 규칙이 자동으로 붙습니다. 하지만 Terraform의 `aws_security_group` 리소스는 다릅니다 — `ingress`/`egress` 블록을 하나라도 쓰기 시작하면, **명시적으로 적지 않은 방향은 전부 차단**됩니다. 즉 egress 블록을 빼먹으면 콘솔의 기본 동작과 다르게 아웃바운드 트래픽이 전면 차단된 보안그룹이 만들어집니다. ChatGPT가 인바운드 규칙에만 집중하다 이 부분을 놓치는 경우가 많아, 이번 Lab의 핵심 검증 포인트 중 하나로 넣었습니다.

**3개로 분리하는 이유**: 하나의 보안그룹에 모든 규칙을 몰아넣으면 "누가 무엇에 접근할 수 있는지"를 규칙만 보고 파악하기 어렵고, 계층별로 다른 팀이 관리하기도 힘듭니다. 계층별로 보안그룹을 나누고 서로 참조하게 만드는 것이 실무에서 가장 흔히 쓰이는 패턴입니다.
