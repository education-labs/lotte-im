# 항목 설명

**왜 모듈을 하나가 아니라 두 개로 나누는가**: VPC·서브넷·보안그룹은 "네트워크가 어떻게 생겼는가"를 다루고, EC2는 "그 네트워크 위에 무엇을 올릴 것인가"를 다룹니다. 이 둘은 변경 주기와 관심사가 다릅니다 — 네트워크 구조는 자주 안 바뀌지만 인스턴스는 계속 늘고 줄어듭니다. 두 관심사를 하나의 모듈에 몰아넣으면, 인스턴스를 하나 더 추가하고 싶을 뿐인데 네트워크 코드까지 같이 손대야 하는 상황이 생깁니다. 계층별로 모듈을 나누면 "네트워크 모듈은 그대로 두고 컴퓨트 모듈만 재사용해서 EC2를 몇 개든 추가"하는 것이 가능해집니다.

**모듈 출력값이 다른 모듈의 입력값이 된다는 것**: `module.vpc.subnet_ids["public-a"]`처럼, 한 모듈의 `output`을 다른 모듈을 호출할 때 `variable` 값으로 그대로 넘길 수 있습니다. 이게 바로 "모듈 조합"입니다. 이렇게 짜두면 `vpc` 모듈 내부에서 서브넷 CIDR을 나중에 바꾸더라도, `ec2-instance` 모듈 호출부 코드는 전혀 손댈 필요가 없습니다 — 루트는 그냥 `module.vpc`가 최신 값을 넘겨주는 것을 받아 쓸 뿐입니다.

**자식 모듈에는 `provider` 블록이 필요 없는 이유**: `modules/vpc`, `modules/ec2-instance` 안에는 `provider "aws" {}` 블록을 넣지 않습니다. 루트에서 정의한 provider 설정을 자식 모듈이 자동으로 상속받기 때문입니다. 자식 모듈 안에 provider 블록을 또 넣으면 오류가 나거나 불필요한 중복이 됩니다.

**`subnet_ids`를 map으로 출력하는 이유**: 서브넷을 하나씩 개별 output(`public_subnet_a_id`, `public_subnet_c_id`, ...)으로 5개나 만드는 대신, `{ "public-a" = "subnet-xxxx", "private-a" = "subnet-yyyy", ... }` 형태의 map 하나로 출력하면 루트에서 `module.vpc.subnet_ids["public-a"]`처럼 이름으로 원하는 서브넷을 골라 쓸 수 있어 코드가 훨씬 짧아집니다.
